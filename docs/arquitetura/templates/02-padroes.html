Padrões e Camadas

Como o código está organizado dentro do serviço. Decisões aplicadas igualmente em todo bounded context — verificadas no CI, não confiadas à disciplina.

Por que Hexagonal

Adotamos Hexagonal (Ports and Adapters) por duas razões concretas:

  1. Testabilidade. O núcleo de domínio não conhece HTTP, EF Core ou SNS. Testes unitários rodam em milissegundos sem mocks complexos.
  2. Substituibilidade. Trocar PostgreSQL por outro banco, ou SNS por Kafka, é trocar um adaptador. O domínio não muda.
▲
Por que não Clean Architecture

Hexagonal e Clean são primos. Escolhemos Hexagonal porque a metáfora ports é mais explícita: cada dependência externa tem uma interface declarada na camada de Aplicação, implementada por um adaptador em Infraestrutura. Clean tem mais camadas e regras de dependência que, na prática deste serviço, não trazem ganho proporcional à complexidade. Registrado em ADR-0002.

As Camadas

Camada Responsabilidade Depende de NÃO pode depender de
Domínio Agregados, value objects, regras de negócio, eventos Nada Nada externo — nem EF, nem AWS SDK, nem Polly
Aplicação Orquestra use cases, define ports (interfaces de saída) Domínio Infraestrutura, Apresentação
Infraestrutura Implementa os ports — repositórios EF, HTTP clients, SNS publisher Domínio, Aplicação Apresentação
Apresentação Recebe HTTP, valida, traduz para command, chama o use case Aplicação Infraestrutura direta (sem atalhos)

Contract-First

APIs são definidas em OpenAPI YAML antes do código. O contrato é a fonte da verdade — quebrar exige PR explícito e bump de versão.

  • Cliente (canais consumidores): gerado via NSwag a partir do YAML, distribuído como NuGet Liquidacao.Client.
  • Servidor: DTOs gerados em build time. Drift entre código e contrato quebra a compilação.
contracts/autorizacao-v1.yaml · trecho
openapi: 3.1.0
info:
  title: Liquidação Transacional
  version: 1.0.0

paths:
  /autorizar:
    post:
      operationId: autorizarTransacao
      parameters:
        - in: header
          name: Idempotency-Key
          required: true
          schema: { type: string, format: uuid }
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: '#/components/schemas/AutorizarRequest' }
      responses:
        '200':
          description: Autorizado
          content:
            application/json:
              schema: { $ref: '#/components/schemas/AutorizarResponse' }
        '422':
          description: Recusado por antifraude ou saldo
          content:
            application/problem+json:
              schema: { $ref: '#/components/schemas/Problem' }

Resiliência (Polly)

Toda chamada externa síncrona é embrulhada em retry + circuit breaker + timeout. Defaults da casa abaixo. Customização exige justificativa em ADR.

Política Default Quando customizar
Retry 3 tentativas, backoff exponencial 200ms · 800ms · 3.2s. Só em 5xx e timeouts. Endpoints idempotentes podem aumentar. Não-idempotentes devem desligar.
Circuit Breaker 5 falhas em 30s → open por 60s Dependência crítica pode pedir threshold mais baixo (3 falhas em 10s).
Timeout 1s por chamada externa Antifraude usa 400ms (latência alvo + buffer pequeno).
Bulkhead 100 chamadas concorrentes por adaptador, 20 em fila Adaptador de baixa criticidade pode ter limites menores.
Program.cs · registro do adaptador antifraude
services.AddHttpClient<IAntifraudeService, AntifraudeAdapter>(client => {
        client.Timeout     = TimeSpan.FromMilliseconds(400);
        client.BaseAddress = config.GetUri("Antifraude:BaseUrl");
    })
    .AddPolicyHandler(GetRetryPolicy())
    .AddPolicyHandler(GetCircuitBreakerPolicy());

static IAsyncPolicy<HttpResponseMessage> GetRetryPolicy() =>
    HttpPolicyExtensions
        .HandleTransientHttpError()
        .Or<TimeoutRejectedException>()
        .WaitAndRetryAsync(
            retryCount: 3,
            sleepDurationProvider: attempt =>
                TimeSpan.FromMilliseconds(200 * Math.Pow(4, attempt - 1)));

static IAsyncPolicy<HttpResponseMessage> GetCircuitBreakerPolicy() =>
    HttpPolicyExtensions
        .HandleTransientHttpError()
        .CircuitBreakerAsync(
            handledEventsAllowedBeforeBreaking: 5,
            durationOfBreak: TimeSpan.FromSeconds(60));

Fitness Functions

Regras arquiteturais não são confiadas à disciplina — são verificadas no CI por testes que falham se forem violadas. Usamos NetArchTest no projeto Liquidacao.Architecture.Tests. Qualquer PR que viole uma regra é bloqueado.

Liquidacao.Architecture.Tests · CamadaTests.cs
public class CamadaTests
{
    [Fact]
    public void Dominio_nao_depende_de_nada_externo()
    {
        var result = Types.InAssembly(typeof(Autorizacao).Assembly)
            .ShouldNot()
            .HaveDependencyOnAny(
                "Microsoft.EntityFrameworkCore",
                "Amazon", "AWSSDK",
                "Polly",
                "System.Net.Http")
            .GetResult();

        Assert.True(result.IsSuccessful,
            $"Domain depende de: {string.Join(", ", result.FailingTypeNames ?? new())}");
    }

    [Fact]
    public void Aplicacao_nao_depende_de_Infraestrutura()
    {
        var result = Types.InAssembly(typeof(AutorizarHandler).Assembly)
            .That()
                .ResideInNamespace("Liquidacao.Application")
            .ShouldNot()
                .HaveDependencyOn("Liquidacao.Infrastructure")
            .GetResult();

        Assert.True(result.IsSuccessful);
    }

    [Fact]
    public void Adapters_implementam_Ports_da_Aplicacao()
    {
        var result = Types.InAssembly(typeof(AntifraudeAdapter).Assembly)
            .That()
                .ResideInNamespace("Liquidacao.Infrastructure")
                .And().AreClasses()
                .And().DoNotHaveNameEndingWith("DbContext")
                .And().DoNotHaveNameEndingWith("Migration")
            .Should()
                .ImplementInterface(typeof(IAntifraudeService))
                .Or().ImplementInterface(typeof(ISaldoRepository))
                .Or().ImplementInterface(typeof(IEventoPublisher))
            .GetResult();

        Assert.True(result.IsSuccessful);
    }
}
▲
Regras invioláveis no CI
  • Domínio não conhece EF Core, AWS SDK, Polly ou qualquer biblioteca externa
  • Aplicação só conhece Domínio e seus próprios Ports
  • Infraestrutura implementa Ports — nunca define novos
  • Apresentação delega para Aplicação, nunca chama Infraestrutura

Adicionando um Bounded Context

Roteiro mínimo para criar um novo contexto sem quebrar as fitness functions. Guia detalhado com exemplo end-to-end em Guia: Nova Feature.

  1. Modele o domínio primeiro. Defina o agregado, suas invariantes e eventos em Liquidacao.Domain/<Contexto>/. Sem mocks ainda — só objetos e testes unitários.
  2. Defina os ports. Identifique quais dependências externas o use case precisa. Crie interfaces em Application/Ports/.
  3. Implemente o use case. Em Application/UseCases/<Contexto>/. Sem HTTP, sem DB — só recebe ports via DI.
  4. Implemente os adaptadores. Em Infrastructure/, cada port ganha implementação concreta com Polly aplicado.
  5. Exponha o endpoint. Adicione em Api/Endpoints/. Mapeie request → command → use case. Retorne Problem+JSON em erros.
  6. Testes na ordem: Domain (unitário) → Application (fakes) → Architecture (NetArchTest verde) → Integration (Testcontainers).
  7. Documente. Crie página 0X-fluxo-<nome>.html seguindo o padrão de 07-fluxo-autorizacao.html.

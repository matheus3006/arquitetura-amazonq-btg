Dados Trafegados

O que entra, o que sai, o que persiste. Estrutura completa do payload, regras de transformação e formato dos eventos publicados.

Payload de Entrada

Todo request chega no endpoint POST /autorizar. Header obrigatório Idempotency-Key identifica unicamente a operação; retentativas com a mesma chave retornam a resposta cacheada por 24h. Campos abaixo formam o objeto AutorizarRequest validado no controller.

Transformação Interna

Entre o request HTTP e o evento publicado, três modelos coexistem. Cada um vive em uma camada diferente e tem responsabilidade distinta.

Modelo Camada Quem cria Propósito
AutorizarRequestApresentaçãoNSwag (gerado do OpenAPI)Contrato HTTP. Validado no controller
AutorizarCommandAplicaçãoEndpoint, ao receber requestInput do use case, sem dependência de HTTP
Autorizacao (agregado)DomínioUse case, via factoryEstado canônico — invariantes garantidas aqui
AutorizacaoCriada (evento)DomínioAgregado, ao mudar de estadoFato passado, publicado via outbox
AutorizarResponseApresentaçãoEndpoint, ao retornarContrato HTTP de saída
▲
Por que não passar o Request direto para o use case

Aplicação não conhece HTTP. Se passarmos o DTO da Apresentação direto, criamos acoplamento que quebra a inversão de dependência. O endpoint constrói o AutorizarCommand a partir do Request. Tradução de uma linha, mas mantém Hexagonal limpo. Verificado por NetArchTest em Padrões § Fitness Functions.

Resposta HTTP

Sempre application/json. Sucesso é 200 OK; recusa de antifraude ou saldo é 422 Unprocessable Entity seguindo RFC 7807 (application/problem+json). Erros internos seguem o mesmo formato.

200 OK · autorizado
{
  "decisionId": "b4c2d3e5-8f9a-4b1c-7d2e-3f4a5b6c7d8e",
  "status": "AUTORIZADO",
  "scoringResult": 87,
  "adviceCode": "APPROVE",
  "authorizationCode": "ABC123",
  "decidedAt": "2026-05-29T18:42:11.247Z"
}
422 · recusado por antifraude
{
  "type": "https://liquidacao.btg.com.br/problems/recusa-antifraude",
  "title": "Transação recusada pelo motor antifraude",
  "status": 422,
  "detail": "Score 23 abaixo do mínimo de 40 para canal POS",
  "decisionId": "b4c2d3e5-8f9a-4b1c-7d2e-3f4a5b6c7d8e",
  "scoringResult": 23,
  "reasonCode": "ANTIFRAUDE_LOW_SCORE",
  "decidedAt": "2026-05-29T18:42:11.198Z"
}

Evento no Outbox

Toda decisão (autorizar, recusar, contingência) gera um evento na tabela outbox_event dentro da mesma transação de banco do agregado. O relay assíncrono publica em SNS. Consumers devem ser idempotentes — o mesmo evento pode chegar mais de uma vez.

Convenções

Item Regra Exemplo
Datas e timestampsISO 8601 com timezone UTC sempre. Precisão até milissegundos no retorno2026-05-29T18:42:11.247Z
IdentificadoresUUID v4 em strings. Nunca inteiros incrementais como ID externoa3f1e2b4-7c8d-4e5f-9a1b-2c3d4e5f6a7b
CPFSem máscara nem pontos. 11 dígitos numéricos12345678901
PANMascarado: 6 primeiros + 6 asteriscos + 4 últimos411111******1234
Valores monetáriosDecimal com 2 casas, ponto como separador. Nunca em centavos247.50
Códigos de moedaISO 4217, 3 letras maiúsculasBRL
Enums em JSONUPPER_SNAKE_CASEAUTORIZADO, PIX_DEBITO
Nomes de campocamelCase no JSON, PascalCase no C#externalTransactionId ↔ ExternalTransactionId
